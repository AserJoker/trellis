# Trellis 里程碑与阶段规划

> 目标：以最小可行路径验证「Model 中心自举」框架的核心闭环，临时措施明确标注，后续阶段完善。

## 总原则

- **临时措施**（T，Temporary）：为在受限环境快速跑通而采用，明确标注「需后续替换/完善」。
- **永久设计**（P，Permanent）：符合最终架构目标，不因临时措施妥协。
- 每阶段结束有**验收标准**，达标才进入下一阶段。

---

## 阶段 0：骨架搭建（当前）

**目标**：确立 monorepo 结构、工具链、设计文档骨架，为后续阶段打底。

**做什么**
- monorepo 结构（core 集中式）：`packages/core`（元数据 + 查询聚合引擎 + function 编排引擎，业务无关，声明 IStore 接口）、`packages/server`（HTTP 服务，将进程内 Model 接口开放到端口）、`packages/store`（实现 core 的 IStore 接口，提供真实存储）、`packages/client`（前端界面，React）
- TS 工具链：tsconfig 继承链、构建脚本
- 设计文档骨架落盘（本文件 + server/client 占位骨架）

**验收标准**
- [ ] monorepo 可 `pnpm install` + `pnpm build` 全量通过
- [ ] 设计文档骨架齐全，每份文档有章节结构与待细化标记

**临时措施**：无

---

## 阶段 1：元数据核心 + JSON 存储（后端地基）

**目标**：Model/Field/Function 的定义、注册、序列化落地，验证自举（Model 的 Model）。

**做什么**
- `core`：Model/Field/Function 的类型定义与校验（查询/编排引擎在 core 但本阶段不实现）
- 系统模型（ModelModel / FieldModel / FunctionModel / 国际化 Model）的定义
- `store`：实现 core 的 `IStore` 接口（JSON 序列化落盘，管理面元数据持久化）
- 元数据注册表：装载/查询/校验 Model 定义

**验收标准**
- [ ] 定义 UserModel（含简单字段 + 复杂字段）可注册、可持久化、可读回，序列化结构稳定
- [ ] ModelModel 能描述 UserModel 自身（自举闭环在代码中成立）
- [ ] 管理面元数据可 JSON 落盘/加载（重启不丢）

**临时措施**
- [T] JSON/内存为 `IStore` 的第一步实现；**待后续**：换真实数据库实现（SQLite/其它）

---

## 阶段 2：后端查询聚合引擎（核心价值验证）

**目标**：验证复杂字段的「物理不存在 + 递归聚合」是框架的核心能力。

**做什么**
- 查询引擎：按 Model 定义递归遍历复杂字段（O2O/O2M/M2O/M2M）
- 关系解析：relationField/referenceField/referenceModel/associationModel 的导航逻辑
- 中间模型处理（O2O/M2M 的 association 表读写）
- 数据清洗：字段裁剪、枚举归一等规范化
- DAO 层：基于元数据封装 create/update/delete/queryOne/queryList/queryPage
- 事务：core 数据源层通过 IStore 的 beginTransaction 获得 ITransactionStore（commit/rollback）
- schema 形状：返回形状（类 JSON Schema 仅形状无约束）+ 白名单裁剪递归查询
- 级联写入：applyRecord(modelId, schema, record) 依据 model 推导 create/update/delete，一次事务应用
- $delete 删除语义：顶层真实删除（O2M 级联）；M2O/O2O/M2M 仅解除关联/删关系

**验收标准**
- [ ] user → auth 的 M2O 查询返回聚合后的 user.auth 对象
- [ ] O2M / O2O / M2M 各自递归聚合正确
- [ ] 复杂字段 store=false 不落库，查询时聚合返回
- [ ] DAO 六操作基于元数据工作，create 自动生成主键、清洗剔除复杂字段
- [ ] 事务失败全量回滚、成功原子提交
- [ ] schema 白名单裁剪 + 关系按子形状递归聚合
- [ ] applyRecord 级联写入一次事务应用，失败整体回滚
- [ ] $delete：顶层真实删除 + O2M 级联；M2M 只删关系不删数据

**临时措施**
- [T] 查询直接内存/JSON 遍历；**待后续**：基于 IStore 适配器优化（阶段 5）
- [T] 事务为内存快照回滚（store 的 JSON/内存实现内）；**待后续**：映射数据库原生事务（阶段 5）

---

## 阶段 3：function 编排引擎（后端行为层）

**目标**：验证 function = JSON 编排图，数据流+控制流合一。

**做什么**
- 原子操作库（原子数据操作：CRUD；原子功能函数）
- 编排图解释器：节点执行、数据流传递、控制流（分支/循环）
- function 作为 Model 的自举描述
- 前后端执行位置标记（`execution: frontend | backend`）

**验收标准**
- [ ] 一个原子操作组合的 function 可解释执行（如：读 user → 过滤 → 聚合 auth）
- [ ] 编排图含分支/循环控制流可正确执行
- [ ] function 定义本身可被 FunctionModel 描述（自举）

**临时措施**
- [T] 编排图解释器为同步实现；**待后续**：异步/并发/错误处理完善（阶段 5）

---

## 阶段 4：前端 ViewModel + 无头组件 + 通讯协议（端到端闭环）

**目标**：验证「XML → 容器绑定 → 组件从父节点取数 → React 渲染」与类 GraphQL 通讯。

**做什么**
- `client`：ViewModel/XML 解析器（0 代码布局描述）
- 非展示容器：绑定 Model/Field；展示组件从父节点取数据
- 无头组件：逻辑层（数据拉取/状态）+ React 适配层（注入渲染）
- 组件类型 Model 化 + 命名空间/版本对应
- 前后端通讯：协议内化于 core（schema 解析是 model 体系的一部分），server 通过 HTTP 暴露 Model 接口，client 数据地图 → server 递归查询
- function 前端执行引擎 + 后端执行封装请求

**验收标准**
- [ ] 一个 XML 描述的界面（含容器绑定 + 展示组件）可渲染
- [ ] 组件事件通过 property 绑定到 Model function，后端执行链路通
- [ ] 数据地图查询返回聚合数据并渲染（含复杂字段聚合）
- [ ] 组件命名空间+版本能正确定位实现

**临时措施**
- [T] 通讯为手写 JSON/请求封装（server 基于 Node 内置 http）；**待后续**：协议规范化（批处理/缓存/订阅）（阶段 5）
- [T] 前端路由/状态管理用最小实现；**待后续**：完善

---

## 阶段 5：完善与抽象（去临时化）

**目标**：替换所有临时措施，抽象到最终架构。

**做什么**
- store 换真实数据库实现：基于 core 的 `IStore` 接口提供 SQLite/其它数据库适配器（JSON/内存实现转测试用）
- 通讯完善：批处理、缓存、错误语义
- 编排引擎完善：异步/并发/错误处理/审计
- 校验器完善：基于 Model 元数据驱动的自研校验
- 模块化初步：热拔插模块机制（元数据 + 前后端代码插件）

**验收标准**
- [ ] store 的 JSON/内存实现与数据库实现可切换（同一 `IStore` 接口）
- [ ] 所有 [T] 临时措施标记清除或转正
- [ ] 模块可装载/卸载，注入元数据与代码插件能力

**临时措施**：无（本阶段目标是去临时化）

---

## 阶段 6：管理面 + 可视化（自举闭环）

**目标**：管理面本身用 View 构建，支持元数据管理，可视化编辑起步。

**做什么**
- 管理面 View（用 View/XML 构建管理界面）
- Model/Field/Function/View 的 CRUD 管理
- 初期 XML/JSON 直接编辑 → 可视化编辑基础
- 模块管理（装载/卸载）

**验收标准**
- [ ] 管理面可创建/编辑 Model、Field、Function、View
- [ ] 管理面自身运行在框架之上（自举，无特例）
- [ ] 可视化编辑可用（拖拽/表单配置基础版）

**临时措施**
- [T] 可视化编辑器初期为表单式配置；**待后续**：完整可视化设计器

| T4 | 编排解释器同步实现 | 3 | 异步/并发/错误处理/审计（5） |

## 阶段依赖

```
阶段0 → 阶段1 → 阶段2 → 阶段3 → 阶段4 → 阶段5 → 阶段6
（骨架）（元数据+存储）（查询聚合）（function）（前端闭环）（去临时化）（管理面）
```

阶段 2/3 可并行（后端内部两条线）；阶段 4 依赖 2/3 的接口稳定。
